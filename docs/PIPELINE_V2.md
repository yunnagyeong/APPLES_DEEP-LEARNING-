# 파이프라인 v2: 무엇을, 왜 바꿨나

7주차까지의 파이프라인을 코드·데이터·실험 결과 전체를 읽고 다시 설계한 기록입니다.
숫자 근거는 모두 저장소 안의 파일(`error_cases.csv`, `data/measure/*`, `results/week7/*`)에서 나왔습니다.

## 1. 진단: 7주차 파이프라인의 문제

| 문제 | 근거 |
|---|---|
| **느림** | 검증 1회당 3.6-flash 3번(원문 claim, 번역문 claim, 뉘앙스) + 임베딩 2번을 순서대로. 재번역 2회면 3.6-flash 9번 → 무료 한도(분당 5회) 때문에 429 대기 발생. 실측 7~65초 |
| **NLI가 하는 일이 없었음** | 사람 라벨 32건에서 NLI가 잡은 오류 7건은 전부 Gemini 뉘앙스 점검도 잡음(NLI만 잡은 오류 0건). 반대로 NLI는 정상 번역 #26을 잘못 거름. 양태(#20 "수 있다→causes"), 정도(#11), 시제(#30) 변화는 entailment로 통과. 원문(한국어)↔번역문(영어) 교차 언어 NLI의 구조적 한계 |
| **NLI 의존성이 무거움** | torch·transformers(수 GB) + 모델 다운로드. "키만 넣고 실행"이 안 됨 |
| **Meaning Score 변별력 부족** | C(원문 claim 보존율)가 32건 전부 1.00. S(임베딩 유사도)는 정상 0.85~0.95 / 오류 0.83~0.91로 겹침. Gemini가 찾은 오류는 점수에 반영 안 돼서 "98점인데 REVIEW" 같은 어긋남 |
| **재번역이 오탐을 못 고침** | #26(정상 번역)은 NLI 오탐으로 재번역 2번을 쓰고도 REVIEW 74.4점. 검증기 쪽 문제는 번역을 바꿔도 안 풀림 |
| **재번역이 처음부터 다시 번역** | 맞던 부분에 새 문제가 생기거나 문체가 흔들릴 수 있음. 그리고 마지막 시도를 그대로 반환해서, 재번역이 더 나빠져도 그 결과가 나감 |
| **실행 안 되던 부분** | `src/baselines.py`가 없어 app.py의 A·B 조건이 실행 불가. 하루 한도가 끝나면 재시도로 몇 분 멈춤 |

## 2. 검증 v2 (`src/verify.py`)

**판정 모델 호출 1번 + 규칙 검사 2개.** 판정 모델에게는 "점수"나 "심각도"를 묻지 않고 **분류만** 시킵니다.

1. 원문을 claim으로 나눔(재번역 시도에서는 첫 시도의 claim을 그대로 고정 → 시도끼리 공정 비교)
2. claim마다 번역문의 대응 구절을 **인용(evidence)** 하고, 정해진 유형 중 하나를 고름
3. 번역문에만 있는 내용을 `MINOR_ADDITION` / `UNSUPPORTED_ADDITION`으로 분류
4. **유형 → 심각도 → 판정·점수는 코드의 고정 표**가 정함 (아래)
5. 판정 모델과 무관한 규칙 검사: **숫자 일치**(원문 숫자가 번역문에 있는지, 번역문에 새 숫자가 생겼는지. `3만`↔`30,000`, `세 가지`↔`three` 처리), **임베딩 유사도 하한**(0.70 미만이면 major)

| 심각도 | 유형 | 판정 | 재번역 |
|---|---|---|---|
| critical | 부정 반전, 숫자·고유명사 변경, 비교 반전, 인과 변경, 의미 반전, **근거·사실 지어냄(UNSUPPORTED_ADDITION)** | FAIL | O |
| major | 확신도 변화(MODALITY), 주관성 표현 손실(ATTRIBUTION), 범위 변화, 조건 누락, 내용 누락, 규칙 검사 | REVIEW | O |
| minor | 시제, 정도 표현, 무해한 단어 추가 | PASS (참고 표시) | X |

"AI가 AI를 평가한다"는 팀의 원래 우려(docs/Verification_Pipeline.md)는 이렇게 줄였습니다: 모델은 인용과 분류만 하고,
결론(심각도·판정·점수)은 사람이 정한 규칙이 내립니다. 판정 결과는 앱에서 인용 구절과 함께 보여 주므로 사람이 바로 확인할 수 있습니다.

## 3. Meaning Score v2 (`src/meaning_score.py`)

```
M = 100 × F × A × G
F = 원문 claim 점수 평균 (OK 1.0 / minor 0.85 / major 0.6 / critical 0)
A = Π(1 − p)   추가 내용마다: 무해한 단어 0.03, 지어낸 내용 0.5
G = 0.6^(규칙 검사 문제 수)
```

판정과 같은 근거에서 나오므로 서로 어긋나지 않습니다. 사람 심각도 순서를 지키도록 정했습니다:

| 사례(사람 심각도) | 판정 | 점수 |
|---|---|---|
| 정상 | PASS | 97~100 |
| 하: 시제·정도 변화 (#11, #18, #30) | PASS | 85~95 |
| 중: 확신도 변화 (#4, #20) | REVIEW | 60 |
| 상: 주관성+확신도 (#1) / 근거 지어냄 (#6, #13, #14, #23) | REVIEW / FAIL | 60 / 30~50 |

가중치는 설계값이고 같은 32건을 보며 정했으므로, **새 문장으로 확인이 필요합니다** (`scripts/eval_verifier.py --cases 새파일.csv`).

## 4. 재번역 (`src/pipeline.py`)

- REVIEW·FAIL일 때만 재번역 (minor는 재번역 안 함)
- **최소 수정**: 판정이 인용한 구절과 유형별 고치는 방법을 주고 "그 구절만 고치고 나머지는 그대로"
- **가장 좋은 시도 반환**: 판정(PASS > REVIEW > FAIL) → 점수 순, 동점이면 앞 시도

## 5. 속도·안정성

| | 7주차 | v2 |
|---|---|---|
| 재번역 없음 | API 7회 (3.6-flash 3) · 약 16초 | 4회 (판정 1) · 약 7초 |
| 재번역 2회 | 19회 (3.6-flash 9) · 약 44초 | 10회 (판정 3) · 약 17초 |

(가짜 API로 실측 지연을 흉내 낸 값. 429 대기 제외)

- 판정 호출과 유사도 임베딩을 동시에 보냄, 원문 임베딩·claim은 시도 간 재사용
- 판정 모델에 `thinking_level="low"` (지원 안 하면 자동으로 빼고 재요청)
- 하루 한도 소진·4xx 오류는 기다리지 않고 바로 처리. 판정 모델 대체(`VERIFY_FALLBACK_MODEL`)는 기본 꺼짐: 유료 API에서는 한도가 문제가 안 되고, 조용히 다른 모델로 판정하면 평가 결과가 섞이기 때문
- 판정 JSON이 깨지거나 claim이 비어 있으면 다시 물음
- app.py: A·B·C 동시 실행, 검색 1회 공유, C 재번역 최대 2회, 검증 결과 패널(문제 유형·인용 구절·시도별 결과)
- 평가 스크립트(`eval_verifier.py`, `run_condition_c.py`)는 `--workers`개 문장을 동시에 처리

## 6. 바꾸지 않은 것과 남은 결정

- **문체 생성 쪽(style_features·generate)은 그대로**입니다. 다만 확인된 한계가 있습니다:
  - 강희 프로필에서 나오는 개인 지시는 "이유는 since/because로" 한 줄뿐이고, 7주차 평가 32문장 중 이 줄이 적용된 문장은 0개.
    즉 7주차 C에서 강희의 개인화는 한국어 RAG 예시로만 들어갔음.
  - 그 한 줄도 강희의 실제 영어 글과 방향이 반대(`data/measure/english_direction_check.json`, causal X).
    팀 규칙(D-008: 평가 데이터로 지시문을 고치지 않음)에 따라 코드는 고치지 않았습니다. 팀 결정 사항.
  - 가장 큰 개선 여지는 **본인 영어 글을 문체 예시로 쓰는 것**입니다. 다만 그러면 7주차 평가 기준(영어 글)과 겹치므로
    영어 글을 예시용/평가용으로 나누는 방식이 필요하고, "한국어 문체 → 영어" 교차 언어라는 연구 주장도 달라집니다. 팀 결정 사항.
- 레거시 검증(`src/verify_legacy.py`)과 7주차 공식(`calculate_legacy_meaning_score`)은 비교·재현용으로 남겨 두었습니다.
