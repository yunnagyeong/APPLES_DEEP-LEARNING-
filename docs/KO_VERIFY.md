# 한→한 문체 변환 의미 검증 (강희 담당)

| 파일 | 역할 |
|---|---|
| `src/ko_verify.py` | 검증기 본체. 입력 글과 변환 결과를 비교해 PASS / REVIEW / FAIL. 재번역 지시·머리말 삭제·REVIEW 표시 함수 포함 |
| `src/ko_pipeline.py` | **변환 → 검증 → FAIL이면 자동 재번역** (`convert_checked`). 데모 앱과 `ko_try.py`가 씀 |
| `scripts/ko_verify_run.py` | 결과 파일 검증. 팀원 결과 파일을 받아 유출 검사 + 검증 → 판정 파일 |
| `scripts/ko_verify_selftest.py` | 검증기 자체 시험(오탐률, 오류 주입 탐지율) |
| `test_ko_pipeline.py` | 재번역 루프 테스트 14개(API 없음, 가짜 생성 모델) |
| `docs/KO_VERIFY.md` | 이 문서 |

- **검증은 API·LLM·torch 없음.** Kiwi(이미 쓰는 형태소 분석기)와 규칙만. 한 건 0.1초 안팎. 같은 입력이면 항상 같은 결과.
- 영어 쪽 `src/verify.py`(Gemini 판정)와는 별개이고 그대로 둔다.

## 변환 → 검증 → 결과별 처리 (`src/ko_pipeline.py`)

```
변환(팀원 convert_style, Gemini 1회) → 규칙 검증
   ├ PASS   → 그대로 둔다
   ├ REVIEW → 고치지 않는다. 문제 문장을 표시해 사람이 그 부분을 주의해서 보게 한다
   └ FAIL   → 기계가 다시 쓴다 → 다시 검증 → 가장 좋은 시도를 돌려준다
               ① 머리말·제목·끝맺음 인사 섞임: 규칙으로 지움 (API 0회, 재번역 횟수에 안 셈)
               ② 빈 출력: 같은 프롬프트로 다시 생성
               ③ 숫자 불일치·예시 베낌 등: "지적된 부분만 고치라"는 최소 수정 프롬프트로 다시 생성
                  (이 프롬프트엔 검색 예시를 넣지 않음 → 예시를 또 베끼지 않음. 문체는 이전 변환문을 그대로 두게 해서 지킴)
               재번역은 최대 1회(max_retries로 바꿈). 고치는 대상은 critical만, major는 사람 몫
```

- **왜 REVIEW는 자동으로 안 고치나:** REVIEW에는 바꿔 말하기를 잘못 잡은 오탐이 섞여 있다(자체 시험 기준 많이 바꾼 글에서 절반). 자동으로 고치면 멀쩡한 문체를 망칠 수 있어, 근거 문장을 강조해 사람이 그 부분만 보게 한다.
- **가장 좋은 시도 반환:** PASS > REVIEW > FAIL, 같으면 앞 시도(원래 문체에 가까움). 재번역이 오히려 나빠져도 첫 결과를 잃지 않는다. 영어 `src/pipeline.py`와 같은 원칙.
- **비용:** PASS·REVIEW는 변환 1회 그대로. FAIL만 생성 호출이 최대 1회 늘어난다. 검증은 0원.
- **평가:** 평가 실험(`scripts/ko_doc_transfer.py`)은 지금처럼 첫 시도로 잰다. 재번역 결과를 평가에 쓸 때는 `first_verdict`(첫 시도)와 최종 판정을 따로 적는다.

```python
from src.ko_pipeline import convert_checked, history_line
r = convert_checked(text, "ganghee")            # convert_style과 같은 인자 + max_retries(기본 1)
r["converted"], r["verify"]                      # 최종(가장 좋은 시도) 변환문과 검증 결과
c = r["check"]
c["status"], c["message"]                        # PASS | REVIEW | FAIL, 화면용 한 줄
c["first_verdict"], c["first_output"]            # 재번역 전 첫 결과
history_line(c)                                  # "FAIL → 지적 부분만 고쳐 다시 생성 → PASS (최종: 2번째 시도)"
c["review"]                                      # REVIEW일 때 사람이 볼 곳 [{sentence, where(source|output), labels, notes}]
```

데모(`app.py` 한→한 탭): 판정 배너 + (재번역했으면) 이력과 첫 변환문 + (REVIEW면) 변환문에서 해당 문장을 형광펜으로 강조하고 목록으로 보여 준다.
`ko_try.py`: `--retries 0`이면 예전처럼 재번역 없이 판정만.

## 역할 나눔

```
[팀원] 짝 예시 DB {AI 글 ↔ 사람 글} 만들기 (Gemini)
            │
[강희] ① pairs : 짝 검사 → 뜻이 바뀐 짝·평가 문서로 만든 짝 제거
            │
[팀원] AI 글 입력 → 짝 예시 검색 → 문체 변환 1회 (Gemini) → 변환결과.jsonl
            │
[강희] ② gen   : 유출 검사 + 의미 검증 → verify.jsonl (PASS/REVIEW/FAIL, use)
            │
[팀원] 작성자 분류 → 정답률 (엄격 = 분류 맞힘 AND PASS)
```

```json

 "input": "<변환 입력: AI가 쓴 일반 글>",
```

## 팀원에게 넘기는 것: `verify.jsonl`

```json
{"id": "...", "cond": "...", "target": "...", "verdict": "PASS", "auto_verdict": "PASS",
 "use": true, "leak": [], "issues": [...], "stats": {"content_recall": 0.8, "style_change": 0.3, "unchanged": false}}
```

- `verdict`: 최종 판정(사람이 확정한 건 그 값), `auto_verdict`: 검증기 판정
- `use`: false면 유출 → 정답률 계산에서 뺀다
- 정답률 계산 쪽에서 쓰는 식: **엄격 정답률 = (분류 맞힘 AND verdict == PASS) 건수 / use == true 건수**
- `stats.unchanged`가 true면 입력을 거의 그대로 낸 것(어절 97% 이상 같음). 많으면 정답률이 입력 판정과 같아진다

## 판정 기준

| 판정 | 유형 | 어떻게 보나 |
|---|---|---|
| FAIL (critical) | 설명·머리말 섞임, 빈 출력 | 첫머리 "다시 쓴 글:", "다음은 … 바꾼", 줄 첫머리 "원문:/예시1:" (입력에도 있으면 제외) |
| | 숫자 불일치 | 아라비아 숫자 비교(3만 = 30,000으로 환산, 세 가지·백 년·이 호선처럼 한글로 쓴 수도 같은 수로 봄) |
| | 검색 예시 베낌 | 예시와 5어절 이상 같은 구절(입력엔 없는 것), 또는 원문 어느 문장도 바꿔 쓴 게 아닌 새 문장의 내용어가 예시에서 옴 |
| REVIEW (major) | 내용 누락 / 추가 | 문장의 내용어(명사·동사·형용사 어간)가 상대 글의 이웃 두 문장 안에 50% 미만 |
| | 부정 뒤집힘 | 부정된 서술어(발생하지 않았다 → '발생')가 대응 문장에서 부정 없이 나옴, 또는 반대. 두 문장을 한 문장으로 합친 경우 합친 두 문장 전체와 비교 |
| | 확신도 변화 | 추측(수 있다·것 같다·보인다·모양이다·듯하다)이 걸린 서술어가 단정으로, 또는 반대 |
| | 범위어 변화 | 모든/모두, 항상/언제나/늘, 반드시, 오직이 생기거나 빠짐(같은 묶음끼리 바뀐 건 변화 아님) |
| | 고유명사 누락, 전체 내용어 재현율 55% 미만 | |
| PASS (minor만) | 형식 변화, 추측 표현 개수만 다름, 약한 범위어(대체로·자주), 강조어(결코·전혀·절대), 수사, 고유명사 추가, **많이 바꿔 씀**(같은 자리 문장이 누락+추가로 동시에 잡힌 짝) | 기록만 함 |

### 부정·추측으로 세지 않는 것 (문체 변환에서 흔한 굳은 말투)

| 겉모양 | 실제 뜻 | 예 |
|---|---|---|
| 부정 수사 의문 | 강한 긍정 | ~이 아니겠는가, ~되지 않으랴, ~살아가지 않으랴마는, ~일이 아니더랴 |
| 이중부정 | 강한 긍정 | ~지 않을 수 없다, ~지 않으면 안 된다 |
| 대조 | A를 넘어 B | A가 아니라 B, 단순히 A가 아니다, A에 그치지/머무르지 않고 |
| 굳은 말 | 부정 아님 | ~에 지나지 않다, 결코 가볍지 않다, ~에 다름 아니다, 다를 바 없다, 두말할 나위 없다, 가감 없이, 쉴 새 없이, 아니면(=또는) |
| -고 말다 | 끝내 ~하다 | 전락하고 만다 (금지 '-지 말다'는 부정으로 셈) |
| 능력·가정의 '수 있다' | 추측 아님 | 뒷받침할 수 있는 환경, 할 수 있어야/있도록/있기 위해, 들을 수 있었다면, ~라 할 수 있다(=~라 하겠다) |
| 보다 | 추측 아님 | 드러내 보이다, 길을 보여 주다, 경향을 보이다, 눈에 보이다 (형용사+'어 보이다'는 추측: 좋아 보인다) |

반대로 '~할 줄 모르다', '~한 적 없다', '~하는 법이 없다', '~할 리 없다'는 부정으로 센다.
한자로 쓴 변환문(魯迅을 追慕하는)은 `hanja` 패키지로 한글 읽기(노신을 추모하는)로 바꿔 비교한다(`pip install hanja`, requirements.txt에 있음).

REVIEW는 "틀렸다"가 아니라 "사람이 볼 것"이다.

부정 '조금 바꾼 글'의 놓친 2건은 '간과할 수 없다→있다'처럼 확신도 변화로 대신 잡힌 것이라 REVIEW는 그대로 뜬다.)

규칙으로 넣은 오류는 실제 LLM 오류보다 찾기 쉽다. 실제 성능은 짝 예시 결과의 REVIEW·PASS 일부를 사람이 읽어 확인한다.

실제로 잡은 의미 변화(기존 결과, 나경 R): "자리 잡았다" → "자리 잡았다**고 볼 수 있다**", "다르다" → "다르다**고 할 수 있다**".
나경 문체로 바꾸면서 단정이 추측이 됨(공통 규칙 '확신 정도 유지' 위반).

- FAIL 7건 중 6건도 오탐이었다: 고유어로 많이 바꾼 문장(경험하다→겪다)의 새 낱말이 예시에 있다고 '예시 내용어 베낌'으로 본 것 3건(원문 문장을 바꿔 쓴 것이면 이제 베낌으로 보지 않음, 예시 구절 5어절 그대로 쓰기는 계속 FAIL), 숫자를 한글로 쓴 것(2호선→이 호선, 100년→백 년). 남은 1건은 예시 구절을 그대로 쓴 진짜 베낌.
- 고유명사 누락 6건은 원문에 섞인 영어 낱말(도구적 Rationality, adult의 눈)을 변환문이 우리말로 옮긴 것과 띄어쓰기(황화 수소/황화수소)였다.
- 부정 오탐의 원인: 11-17 '아니하다' 수정이 main에 빠져 있었음, 수사 의문(~아니겠소·~않으랴), 대조(~가 아니라·그치지 않고), 이중부정, '-고 말다', 낱말 속 '없'(가감 없이), 한자 표기, 문장 합치기.
- 남은 REVIEW 34건 중 10건은 변환문이 추측을 덧붙인 글이고, 6건은 누락·추가만 남은 글이다.
- 남은 확신도 28건 중 24건은 변환문이 '~한 모양이다', '~인 것 같다'를 덧붙인 것 → **실제 확신도 변화**(공통 규칙 '확신 정도 유지' 위반). 생성 프롬프트에서 막는 게 맞다.
- 남은 누락·추가는 대부분 같은 자리 문장을 고유어로 많이 바꿔 쓴 것(이광수 문체: 자율성→자립, 노동 환경→일자리 판). 겹침이 20% 미만이라 짝을 못 지은 경우다. 문턱을 더 낮추면 다른 문장으로 바꿔치기한 것도 '바꿔 씀'으로 통과돼서 낮추지 않았다.
- 진짜로 볼 것의 예: '믿어 마지않는다'를 '의심하여 마지않는다'로 쓴 문장(뜻이 반대), '눈에 보이지도 않는'처럼 원문에 없는 설명 추가.

## 짝 예시라서 특히 조심할 것 (팀원과 공유)

1. **정답 유출**: 평가 입력이 사람 문단 P를 AI 말투로 바꾼 것이고 짝 DB에 (AI(P), P)가 있으면, 검색이 그 짝을 찾아 P를 베낀다 → 정답률이 가짜로 오른다. 짝 DB는 학습 문서(`data/eval/split_info.json`의 heldout 제외)로만 만든다. `gen`이 잡은 건은 `use=false`.
2. **짝의 AI 글도 뜻이 바뀔 수 있다**: 기존 중립화 결과에도 "변화시킬 수 있다 → 변화한다"가 있었다. 뜻이 바뀐 짝을 넣으면 모델이 뜻 바꾸기를 배운다 → `pairs`로 먼저 거른다.
3. **예시 베끼기**: 분류기는 학습한 사람 글을 알아보므로 예시 문장을 베끼면 쉽게 맞는다 → 베낌은 FAIL.

## 한계

- 반의어 바꿔 말하기('얻지 못하다'→'잃다', '불변하는'→'흔들리지 않는', '가변성'→'뒤바뀔 수 있고'), 동의어로 많이 바꾼 문장은 오탐하기 쉽다(같다↔다르지 않다 등 흔한 짝은 처리함).
- '~에 그치지 않는다'는 늘 대조로 보므로 '그쳤다↔그치지 않았다'의 진짜 뒤집힘은 놓칠 수 있다. 문체를 많이 바꿀수록 REVIEW가 는다.
- 같은 낱말로 인과·비교 방향만 바꾼 것("A 때문에 B" → "B 때문에 A")은 못 잡는다.
